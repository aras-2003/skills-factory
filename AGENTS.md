# Skills Factory agent instructions

For Skills Factory Cloud Next or Site changes/publication, read `docs/SITES-PUBLISHING.md` from this repository's current main and the installed Sites hosting skill. The canonical MCP adapter is `adapters/skills-factory-cloud-next/`; the Site application is `sites/skills-factory-site/`. The provider-managed Site repository is a deployment mirror only; never author changes there without first applying them here.

A user publication request authorizes ordinary in-scope work. Network/terminal approval and credential-delivery approval are separately enforced. Hidden stdin prevents display but does not authorize transfer. DNS failure is not an approval rejection; use the runbook's reviewed execution path. If credential delivery is explicitly rejected, stop that path, preserve edits and report the actual reason. Do not reroute a rejected transfer or assume a model/chat switch supplies permission. Do not invent a user approval button.

GitHub main and the provider-managed Sites deployment mirror are separate. GitHub main updates do not publish the Site automatically. Generate the Cloud Next adapter bundle, Site catalog and canonical source attestation from the same Skills Factory commit, then synchronize the Site workspace with `sites/skills-factory-site/scripts/sync-site-source.mjs` inside the official Sites workflow. Use native deployment tools; Git inside that workflow is expected. Preserve source history, Site/plugin identity and audience. Confirm the actual deployed version and mirror SHA separately from the canonical Skills Factory SHA and embedded Lab provenance. For Chat tests, explicitly select Cloud Next and verify actual tool invocation.

For development, test scope, task states, WIP, evidence and release gates, follow `docs/governance/SDLC-OPERATING-PROCESS.md` (owner-approved D1–D8). Use native Project stages and Architecture Impact A0–A4. The former repository-wide single-active-iteration rule is superseded: independent packages may proceed within development WIP 2 and one shared Lab lane. Preserve frozen historical acceptance; never infer runtime PASS from CI, loading or a documentation update.

## Codex Luna-first delegation pilot (#748)

For project-scoped Codex development in a trusted checkout, follow `docs/governance/CODEX-SUBAGENT-PILOT.md` and `.codex/config.toml`. The main chat is coordinator and implementation owner; the project default is Luna High, though explicit host selection may override it. The project config declares the primary default but cannot prove the effective host model.

Use the role-specific agents: `sf-architect` for A2 decisions affecting a capability boundary, shared contract, or material dependency; required A3–A4 software-architecture advice; and A1 changes that affect a shared public contract or trust boundary; `sf-developer-medium` or `sf-developer-high` for explicitly bounded implementation; `sf-test-designer` before implementation; `sf-test-executor` for bounded exact-SHA checks; `sf-independent-reviewer` for risk-required independent review; `sf-skill-evaluator` for frozen baseline/candidate evaluation; `sf-researcher-low` or `sf-researcher-medium` for assigned research; and `sf-release-evidence` for evidence reconciliation. For software-repository architecture work, dispatch the named `sf-architect` profile (`gpt-6.2-sol`, high). OAF skill/workflow model-class guidance applies to execution of that OAF capability and does not select or override a Codex role profile. Keep at most two child threads active. Assign one writer per shared contract and use compact, source-linked handoffs.

Do not spawn agents for trivial A0 edits by default. Test design and execution are separate roles. A separate child thread does not establish an OS-level sandbox or prove a different model. The executor must not edit source or tests; behavioral instructions do not change host permissions. A required delegated gate needs an observed child thread, exact candidate SHA, actual command/output/exit status and case scope. If spawning or a required model is unavailable, mark the gate BLOCKED/NOT_RUN; do not simulate it. CI success does not establish independent review, runtime acceptance or production authorization.

Record both Architect `INVOKE` and `SKIP` decisions before the first dependent action; include only sanitized signals and safe evidence references. A dispatch receipt is not a runtime/model quality PASS. Validate records with `python scripts/eval/role_decision_record.py validate` and link the sidecar from the existing Issue/PR or eval receipt.
